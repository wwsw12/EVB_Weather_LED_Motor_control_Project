# 05. 트러블슈팅과 코드 검토

> 문서 분석 당시 대상 폴더와 상위 경로에서 Git 저장소를 찾지 못했고 프로젝트 내 디버깅 로그·변경 기록도 확인되지 않았습니다. 아래 소스 검토는 실제 장애 재현이나 해결 이력이 아닙니다. 펌웨어는 수정하지 않았습니다.

## 1. 확인된 실제 문제 해결 사례

현재 **근거 없음**. 현상 → 처음의 가설 → 확인 과정 → 원인 → 수정 내용 → 검증 결과를 뒷받침할 자료가 없어 사건을 작성하지 않습니다.

## 2. 코드에서 확인되는 설계 대응

| 코드상 대응 | 확인된 동작 | 해석과 미확인 사항 |
|---|---|---|
| ADC DMA circular | 두 ADC 결과가 메모리에 반복 기록됨 | 변환마다 CPU가 직접 읽지 않는 구성. 성능 개선량은 측정되지 않음 |
| 홀딩 진입 | PWM 비교값 0, 모터 제어 핀 두 개 Low | 정지 출력을 의도한 것으로 해석. 물리적인 정지 여부·응답시간은 미검증 |
| 홀딩 `PLAY` | `previous_moter_mode=0`과 X 기준 초기화 | 이후 선택된 모드의 출력 갱신과 새 X 기준 설정을 유도. 동작 성공 기록은 없음 |
| 모드 변경 시만 모터 갱신·로그 | 현재 모드와 직전 모드를 비교 | 동일 모드 반복 출력을 줄이는 구조. 실행 이력과 시간 절약량은 없음 |

## 3. 소스 검토에서 발견한 미해결 문제

| 항목 / 근거 | 가능한 영향 | 수정·검증 제안 |
|---|---|---|
| **홀딩 중 END 이후 출력**: [main.c](../Core/Src/main.c)의 `holding_function()`은 `END`에서 `moter_mode`를 지우지 않고 반환. 호출한 `START` 분기 이후 같은 반복에서 모드 변경 블록 실행 | 홀딩 진입 직전 선택된 모드가 `previous_moter_mode`와 다르면 정지 직후 PA6과 PWM이 다시 켜질 수 있음. 실기 재현은 없음 | 상태 전이를 명시하고 END 시 모드·이전 모드 초기화 및 같은 반복의 구동 차단. 파형과 회귀 테스트로 확인 |
| **UART 경계 검사 부재**: `rx_buffer[50]`에 `rx_buffer[rx_index++]`를 제한 없이 기록 | 긴 입력에서 배열 범위를 벗어나 메모리 손상 가능 | 최대 49문자 제한, 초과 입력 폐기 및 명시적 오류 처리 테스트 |
| **명령 수신 공유**: `rx_flag`는 첫 바이트부터 1이고 초기화되지 않음. ISR이 `rx_buffer`를 쓰는 동안 루프와 홀딩은 같은 배열에 `strcmp`, `PLAY`에서는 `strcpy` | 개행 전의 부분 문자열·이전 명령 조합을 비교하거나 수신 중 쓰기가 충돌할 수 있음. 명령 처리 시점 보장 불가 | 완성 플래그를 개행 시에만 게시하고 별도 버퍼/큐와 짧은 임계 구역 등으로 소유권을 분리 |
| **인터럽트 공유 변수**: `rx_flag`, `rx_buffer`는 ISR과 메인 코드에서 공유되지만 `volatile` 및 명시적인 동기화가 없음 | 최적화 시 변경 관찰이 보장되지 않고 문자열 일관성도 보장되지 않음 | 공유 상태의 컴파일러 가시성과 원자적 전달을 함께 설계. `volatile`만으로 버퍼 경합은 해결되지 않음 |
| **0과 재시작 경계**: 평균 0은 어떤 조도 분기도 선택하지 않음; 일반 `END` 분기는 `first_x_value`를 초기화하지 않음 | 0 입력 시 이전 모드 유지 가능; 일반 END 후 START 시 이전 X와 새 X 차이로 홀딩할 가능성 | 0의 의미를 명시해 안전 기본값 정의, 재시작 시 X 기준 초기화 후 경계값 테스트 |
| **10회 평균과 X 차이**: 루프 읽기 시점은 ADC 변환 완료나 고정 주기와 동기화되지 않음 | 평균에 중복 샘플 포함, 차이의 시간 간격이 일정하지 않음 | DMA 완료 기준 샘플 큐 또는 타이머 기반 샘플링, 필터·임계값 교정 및 실측 |
| **DMA IRQ 부하**: 2 halfword 순환 전송에 HAL이 half/complete 인터럽트를 모두 활성화하고 IRQ 우선순위는 SysTick보다 높음 | 잦은 IRQ가 루프·UART·틱 응답성에 영향을 줄 가능성. 부하량은 미측정 | 오실로스코프나 계측으로 IRQ 빈도·CPU 부하 확인 후 버퍼 크기와 IRQ 정책 검토 |
| **실패 처리**: 앱이 ADC 보정·DMA 시작·UART 수신 재등록·PWM 시작 및 UART 송신의 반환값을 무시 | 주변장치 오류를 인지하거나 복구하지 못할 수 있음 | 반환값·UART 오류 콜백 점검, 안전 상태 전이와 오류 기록을 설계 |
| **출력 함수**: `__io_putchar`는 `int`형인데 반환문이 없음 | 컴파일 경고 가능. 호출자가 반환값을 사용하면 정의되지 않은 동작; 현재 `_write`는 반환값을 사용하지 않음 | 정상 전송 시 문자 반환, 실패 정책 정의 후 재빌드 |

이 목록은 코드 경로를 근거로 한 위험과 제안입니다. 실제 고장 빈도나 재현 여부는 확인하지 않았으며, 특히 모터는 안전한 시험 장치에서 검증해야 합니다.

## 4. 개발자 설명과 실측 자료가 필요한 항목

- 실제 경험한 사례: **문제 현상 → 처음의 가설 → 어떤 측정으로 생각을 바꾸었는지 → 원인 → 변경 전후 코드 → 재시험 결과**.
- 회로도·BOM·보드 및 센서/모터 드라이버 모델, LED 극성·배선.
- UART 명령 입력 방식과 CR/LF 설정, 정지·재개 의도, X축 임계값 500의 선정 근거.
- ADC 입력·PWM·UART 로그/파형, 실기 조건, 이전 빌드와 소스의 대응 기록.
